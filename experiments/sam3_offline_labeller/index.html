    SAM 3 / SAM 3.1 as a slow, offline, background ball labeller¶

    Naming note: the held-out match used to be called "Norwich"; it is Arsenal v Nottingham Forest (scoreboard NFO), now arsenal_nottinghamforest. Old ids (arsenal_norwich_segNNN, *_norwich dirs) and experiment artifacts written under the old name (r3_norwich, exp/temporal/round3/norwich*, S3 exp_temporal_r3/out/*_norwich) keep it, so old numbers can still be traced.

    Branch exp/sam3-offline-labeller (from exp/temporal-detector @ 331ae64). Code: experiments/sam3_offline/ (README there), Prefect flows ~/code/jobs/footy_sam3.py + sam3.prefect.yaml, numbers: docs/experiments/sam3_offline_labeller.json (+ experiments/sam3_offline/results/), sheets: docs/experiments/sam3_offline_labeller/. Builds on temporal_detector_round3.md (held-out list, 50 fps handling, S1 gate, SAM2.1-small crop512 tracker). All GPU runs were Prefect flow runs on the gpu pool (desktop RTX 2070 8 GB), one at a time.

    Question. Can SAM 3 / 3.1 label balls offline: one known frame (a confident RT-DETR box, an overview, a human click) -> track forwards and backwards through long stretches -> labels written by a queued background job? Speed does not matter, offline quality and throughput do.

    Answers in brief¶

    1. How far does one seed carry? SAM 3 is no better than the SAM2.1-small crop512 tracker we already have. Held-out clips + the 359-frame Aston Villa run, oracle seeds (1 217 scored frames): recall@10 0.943 (SAM 3) vs 0.945 (SAM2.1), paired -0.002 [-0.007, +0.004]; on the six sparse held-out clips both are at 1.000 (251 frames, up to 100-250 frames from the seed); with RT-DETR conf >= 0.8 seeds both are 0.996 (228 frames). The only place SAM 3 separates is arsenal_example (an out-of-play ball in the crowd, practically invisible): 0.301 vs 0.250 (+0.051 [+0.032, +0.072], one clip; both useless). The set is saturated, so it cannot show a gain and does not show one; SAM 3 costs 3x the time (2.4 vs 7.0 frames/s) and 6x the memory (4.9 vs 0.8 GB). SAM 3.1 (multiplex) is equal to SAM 3 here (0.928 vs 0.932 on dev) and slower (2.1 fps, 6.2 GB).
    2. What helps. A box seed (box ~ box + point > point-only: -0.020), a crop that follows the ball at 512 px (round-3 size; 768 is the same, 384 -0.020, 256 -0.244, no crop -0.039), fp16 (fp32 gives identical labels at 3.2x the time). What does not: text prompts as the tracker (0.73 / 0.63 vs 0.98, no memory), frame_step 2 (2x faster but -0.051), the "offload state to CPU" memory setting (-0.28, a bug-like loss and no VRAM saved), crop 256. Gating: SAM 3's object-score logit is a better gate than SAM2's (score > 8: precision 0.996 at 59 % coverage vs 1.0 at 37 %); the S1 gate (forward track of seed a x backward track of seed b within 5 px) was right 14/14 times in the production demo, whereas a score gate cannot catch a false seed (an RT-DETR conf 0.818 "ball" on a yellow boot was tracked as a boot for ~90 frames with logit 8-10). Recovery and the rest of the tricks: see the sections below.
    3. SAM 3 as a seed finder is the real finding. Text prompt "ball" on 384 px tiles upscaled to 1008: top-1 hit@10 0.85 vs RT-DETR-L 0.60 on the same 94 held-out GT frames (Bournemouth 0.85 vs 0.51; Man City 0.86 vs 0.90), any-candidate recall 0.96 vs 0.71. "yellow ball" is equal on Bournemouth (0.86) and useless on a white ball (0.00): the prompt must follow the match. Whole-frame text detection (one 1008 px pass) is already 0.76; 540 px tiles are worse (0.71); "white ball" / "small white ball" fail (0.14 / 0.11). It costs ~5-6 s per frame at 384 px tiles (15 tiles). So SAM 3 can find its own seeds, slowly. Caveat: on the 80 dev frames (clips RT-DETR was trained on, many blurred in-play balls) it is worse than RT-DETR (0.64 vs 0.85), so the claim holds for footage RT-DETR has not seen.
    4. Throughput / cost on the RTX 2070. SAM 3 tracker 0.42 s/frame (2.38 fps) after a bf16 patch (see Setup; unpatched 0.75 s), SAM 3.1 0.48 s, SAM2.1 0.14 s. A match half (~70 k frames at 25 fps): 8.2 GPU-hours for one pass over every frame with SAM 3 (2.7 h with SAM2.1), 16.4 h if every frame is covered twice for the S1 gate, 2.5 h if SAM 3 only fills the ~30 % of frames the detectors miss; 1.1 h of seed finding per half at one 384-tile probe every 100 frames.

    Recommendation (details at the end): do not replace SAM2.1 in the pseudo-label pipeline with SAM 3 / 3.1 as the tracker. Make SAM 3 the background seed finder and seed verifier (text prompt on 384 px tiles, per-match prompt), keep SAM2.1 crop512 as the track engine, and use S1 (two-seed agreement) rather than scores as the trust signal. Use the SAM 3 tracker only for stretches where SAM2 is known to fail (crowd / long occlusion), where it showed its only, small, gain.

Dev (SAM 3 box crop512): 82 % of misses are "tracker reports absent" (a camera cut ends the track: the crop follows the old position), 9 % drift 10-50 px, 9 % wrong object; SAM2: 85 % absent, 15 % wrong object. A track must be stopped at a cut (not done here; the S1 gate would reject the frames after it).

    Setup (desktop, RTX 2070 8 GB)¶

    • Separate venv ~/sam3-exp/venv (python 3.12, torch 2.8.0+cu128, numpy 1.26.4); upstream facebookresearch/sam3 @ eef6839 (2026-11-13) installed editable from ~/sam3-exp/sam3_src. Not ultralytics 8.4.213: its SAM3VideoPredictor is the frame-by-frame predictor pipeline, its 3.1 support is image / point only, whereas the upstream tracker has the SAM2-style init_state / add_new_points_or_box / propagate_in_video API the round-3 crop-following driver needs. Nothing was installed into ~/sam2-exp/venv, the jobs venv or the footy venv.
    • Weights: sam3.pt (sha256 9999e234..., identical to the mini copy) and sam3.1_multiplex.pt (complete, 3 502 755 717 bytes) pulled from S3 with presigned urls.
    • Licence: SAM License (Meta, 2025-11-19): royalty-free, worldwide, non-exclusive licence to use / modify / distribute the SAM Materials; redistribution of the model or derivatives only under the same agreement (include a copy); publications of research done with it must acknowledge the use; no use for ITAR / military / weapons / espionage or trade-control-prohibited ends; the licence terminates if we sue Meta over the materials; "AS IS". Fine for an internal labelling pipeline; keep the licence text with any redistributed weights. (pyproject says "MIT" in a classifier, the LICENSE file is the SAM License.) Dependencies: timm, ftfy, regex, iopath, huggingface_hub (unused with a local checkpoint), numpy < 2; no flash-attn / triton on sm_75.
    • RTX 2070 (sm_75) patches, applied as runtime monkeypatches in sam3_track.patch_turing (upstream untouched):
    • sam3.perflib.fused.addmm_act (ViT MLP fc1 + GELU) hard-casts to bfloat16; sm_75 has no bf16 tensor cores, so cuBLAS ran an emulated magma_sgemmEx<bf16> kernel = 59 % of the backbone time. Plain fp16 autocast: backbone 0.63 -> 0.29 s per 1008 px frame (2.1x), tracker 0.75 -> 0.42 s per frame.
    • The upstream constructors enter a global bf16 autocast (bf16_context.__enter__()); it is exited right after building and runs use torch.autocast(fp16). No fp16 overflow / NaN observed.
    • SAM 3.1: decoder.functional_attention forces the FlashAttention SDPA backend ("No available kernel" on Turing) -> efficient / math backends. The standalone 3.1 tracker also needs tracker.backbone = detector.backbone and forward_image(need_sam3_out=False); the multiplex demo tracker has no box prompt: "box" = the ellipse inscribed in the box as a mask prompt, "point" = the centre point.
    • Precision / memory (2 dev clips, 1 seed each, 60 frames, 186 frames scored): fp16 autocast 0.995 recall, 2.38 fps, 4.9 GB peak (fp32 weights resident + fp16 copies cached by autocast); fp32 identical labels (paired +0.000) at 0.74 fps (3.2x slower), 4.3 GB; memory selection off (apply_temporal_disambiguation=False) 1.000 (+0.005 [+0.000, +0.019], n.s.); offload_state_to_cpu 0.715 (-0.280), VRAM unchanged (4.8 GB: the weights dominate) -> do not use. Weights are 3.4 GB in fp32; a half-precision copy of the backbone would free ~2 GB if more headroom is needed (not needed: 8 GB fit, long clips are fine because frames are injected one at a time and per-frame state is ~1 MB; whole-match tracks prune state older than 300 frames, prune_age).

    • The crop is the biggest lever, with a plateau at 512-768 px: a 256 px window loses the ball whenever it moves fast (-0.24), 384 -0.02, no crop -0.04 (SAM 3 on the squashed 1080p frame still works: the ball is 5-6 px there). Compute is identical for every crop (the model always sees 1008 px), so "upscale the crop to the native input" is free and automatic; upscaling more (smaller crops) does not help, a larger field of view does.
    • Box seed (with or without the centre point) > point only. SAM 3.1 behaves like SAM 3 (same recall within noise, higher precision, lower coverage, +20 % time, +1.3 GB): its multiplex advantage is for many simultaneous objects, not for one ball.
    • Text prompts as the tracker (no seed memory: per frame, text detection on the crop around the last position, nearest candidate, text:ball 0.725 [0.679, 0.775], text:yellow ball 0.630 (white-ball Man City clips included), reach 80, 346 samples) lose 0.26-0.35 against the box-seeded tracker (0.983): the detector alone drops the ball (coverage 0.73) although what it emits is 99.6 % correct. Text belongs in seed finding / recovery, not in tracking.
    • frame_step 2 doubles throughput (4.75 effective fps) but costs 0.051 recall: linear interpolation over the skipped frame fails on kicks.

    Gating¶

    • Object-score logit (own presence head). Raising the gate trades coverage for precision; SAM 3's score is the more informative one. Held-out + Aston Villa, oracle seeds: gate 0 / 4 / 6 / 8: SAM 3 coverage 0.98 / 0.94 / 0.87 / 0.59 with precision 0.961 / 0.964 / 0.974 / 0.996; SAM2 0.99 / 0.91 / 0.84 / 0.37 with 0.957 / 0.969 / 0.972 / 1.000. On arsenal_example gate 8: SAM 3 coverage 0.17, precision 0.966 (recall 0.164) vs SAM2 coverage 0.02: SAM 3's scores separate the few correct frames from the crowd; SAM2's do not. (The 0.96 baseline precision is the 10-11 px near-misses of one clip.)
    • S1 (forward track of seed a, backward track of the next seed b, agree within 5 px): with oracle seeds all 217 GT frames between seeds pass and are correct for both models (nothing to reject). In the production demo with RT-DETR seeds on Bournemouth seg035 (below) S1-gated frames were 14 / 14 correct while single-track score-gated frames were 24 frames at only 67 %: the wrong ones come from a false seed.
    • SAM 3 x SAM2 agreement (within 5 px, oracle seeds, held-out + Aston Villa): coverage 0.974, recall 0.937, no precision gain (both make the same 10-11 px drift errors); it is a useful independent-model check against false seeds, not against labelling noise.
    • Lesson (production demo): a wrong seed (RT-DETR conf 0.818 "ball" = a yellow boot at seg035 frame 58) gives a confident, consistent track (logit 8-10, 90+ frames): demo_labels_bournemouth_seg035.jpg. No score gate can catch it; agreement between independent seeds (S1) or a seed check can.

    Recovering lost tracks¶

    Implemented in sam3_track.py (config recover): after loss_k = 3 consecutive lost frames (mask empty or score logit < 0), search around the last confident position (radius 150 px, 512 px crop) and re-seed the tracker with the nearest candidate as a new conditioning box, then continue propagating. Candidates from (a) SAM 3 text detection text:ball on the crop (score >= 0.3) or (b) RT-DETR candidates (conf >= 0.5, cands, the "re-seed from detector candidates" variant). Ablation on the final oracle set, SAM 3 box crop512, reach 400 (astonvilla_seg080, arsenal_example, bournemouth seg035; (b) on the last two): the recovery never fired (0 re-seeds in every track), results are identical to the baseline (0.929 / 0.301 / 1.000). The loss events in these clips are a camera cut or a ball that is not visible (crowd), where there is no candidate within the search radius; the held-out set has no loss that a nearby detection could repair. So the benefit of recovery is unmeasured, and the re-seed code path was never exercised on real data (treat it as untested); a test needs footage with occlusions behind players / long kicks that the tracker loses but a detector still sees (the dev drift case mancity_seg010 o2 backward is such a case, but only 2 of the dev tracks lose the ball). Text detection as a seed finder is the part that works (below). Not done: RT-DETR / text recovery for SAM 3.1 (its detector API differs), re-seeding on a second SAM2 opinion.

    Queue a whole match¶

    1. Seeds file on the mini (JSONL, one row per seed; box or xy, original frame index): from RT-DETR machine labels python experiments/sam3_offline/make_seeds.py --labels <machine_labels dir> --video-dir <clips dir> --thr 0.8 --spacing 100 > /mnt/storage/exp/sam3/<match>/seeds.jsonl (best conf >= 0.8 ball per 100-frame window; Bournemouth round-3 labels: --index-stride 2). Human clicks / overview seeds are appended in the same format ({"clip": .., "frame": .., "xy": [x, y], "source": "human"}).
    2. Segment clips named <clip>.mp4 in one directory on the mini (or a clip_files map {clip: file name}).
    3. $PF run sam3-label-match/sam3-label-match match=<name> seeds=/mnt/storage/exp/sam3/<name>/seeds.jsonl clips_dir=<mini dir> reach=250 overlap=15 'config={"model":"sam3","prompt":"box","crop":512}'
    4. leave it: per clip the video is staged (S3 presigned GET sam3/<match>/<clip>.mp4 when prepared, else rsync), sam3_label.py runs forward + backward tracks per seed (never past the neighbouring seed + overlap), writes <clip>.labels.jsonl + <clip>.raw.json.gz, pushes them to /mnt/storage/exp/sam3/<match>/labels/, deletes the staged video. Cancel / retry / crash-resume keeps finished clips and finished tracks.
    5. Output rows (JSONL, one per labelled frame): clip, p, frame (original index), x, y, box, score (SAM object-score logit), seed, dir, dist (frames from the seed), gate: seed (the seed itself) | s1 (forward track of one seed and backward track of the next agree within 5 px: position = mean) | score (single track, logit > score_gate) | weak (the rest: do not use as a label).

    Demo (sam3-label-match match=demo, Bournemouth seg035, 3 RT-DETR seeds at original frames 58, 116, 270, reach 150): 39 GT frames inside the labelled span: seed 1/1, s1 14/14 correct, score-gated 24 frames 66.7 % correct (the errors all come from seed 58, a yellow boot). eval_labels.py reproduces it; demo_labels_bournemouth_seg035.jpg shows the labels (magenta = seed, green = s1, yellow = score gate).

    Caveats¶

    • The held-out GT is saturated for tracking from a good seed: differences between SAM2 / SAM 3 / 3.1 are below what 251-1 217 frames of 7-8 clips can resolve (clip-level CIs are wide; frame-level CIs are optimistic). A harder, denser GT with fast kicks / occlusions would be needed to rank trackers.
    • The 250+ bin is one clip; arsenal_example is one clip; no-ball precision has n = 5-26; Nottingham Forest could not be scored (no window labels).
    • Odd-frame GT of 50 fps clips is scored against the mean of two neighbours (adds up to a few px of interpolation error); 10 px hit threshold equals about the ball diameter.
    • Seed-finder prompts were not tuned on a separate set before the held-out numbers were read (a dev check is reported); the "yellow ball" result is match-specific by construction.
    • SAM 3.1 was tested with mask / point seeds only (no box prompt in the multiplex demo tracker) and only on the dev set; the text-recovery trick is implemented for SAM 3 only.
    • fp16 autocast with fp32 resident weights; no torch.compile, no lower input resolution (the tracker is hard-wired to 1008 px / 72x72 features; a 504 px variant would need re-deriving the RoPE / memory sizes and was not tried).

    Recommendation and next step¶

    1. Keep SAM2.1-small crop512 as the track engine of the pseudo-label pipeline: same accuracy as SAM 3 / 3.1 wherever the GT can tell (saturated), 3x faster, 6x less memory, 2.7 GPU-hours per half. SAM 3.1's multiplex gains do not apply to one ball.
    2. Use SAM 3 as the slow background seed finder and verifier: (a) per match pick the text prompt (white ball: "ball" / "soccer ball"; yellow ball: "ball" / "yellow ball"; check on a few dev frames), (b) probe 384 px tiles upscaled to 1008 every ~50-100 frames (1-2 h per half) and add the top detection (score >= 0.5: ~95 % right) as a seed candidate next to RT-DETR conf >= 0.8 seeds, (c) accept a track only where two independent seeds agree (S1, 5 px) or a second model (SAM 3 vs SAM2.1) agrees; do not trust a single track's score (false seed = confident wrong track).
    3. Use the SAM 3 tracker only on stretches where SAM2 loses the ball (crowd / long occlusion): it was the only place it beat SAM2 (+0.05 on arsenal_example, +0.17 at 100-250 frames, one clip) and its logit is the better gate (score > 8: precision 0.97-1.0).
    4. Production: sam3-label-match (built, demoed): ~0.42 s per tracked frame; give it seeds from (2); budget ~8 GPU-hours per half for one SAM 3 pass over every frame, ~2.5-4 h for gap filling, overnight is fine.

    Next steps, in order: (i) a harder, denser GT (fast kicks, occlusions, crowd) because the current held-out set cannot rank trackers; (ii) stop tracks at scene cuts (cuts.py) and add the SAM 3 text probe as a seed verifier in sam3_label.py; (iii) run the seed finder + SAM2 tracks on an unlabelled half (Nottingham Forest) and measure the precision of the S1-gated labels with the blind Ball Check (the study could not score Nottingham Forest: no window labels); (iv) feed the SAM 3 text detections as extra candidates to the round-3 B1 solver (union with RT-DETR gave +0.03-0.04 recall before); (v) only if throughput matters, try a 504 px SAM 3 input (4x fewer tokens; needs the RoPE / memory feature sizes re-derived) or half-precision weights.
