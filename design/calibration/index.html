    Calibration (camera → pitch) — Implementation & Inspection Plan¶

    Status: PLAN · Stage §2.3 of system_design.md · Feeds §2.6 projection.md · KB bead ft-wn9

    Goal: for every broadcast frame, estimate the image→pitch mapping so that detection boxes become (x, y) in pitch metres. Output lands in the feature store's source-tagged calibration table (see "Feature store" below; the old inline frame.homography columns are deprecated), and the existing PitchProjector logic consumes it.

    0. What already exists (and what doesn't)¶

    Piece State
    projection/projector.py — PitchProjector (anchor = bottom-centre for players, centroid for ball; NaN on low quality) Written + unit-tested, never fed a real H
    Feature store calibration / pitch_keypoint tables, frame_calibration_best and detections_on_pitch views, GT/proposal importer Implemented (see below)
    Broadcast classifier (classifier.py) — gates which frames are main-camera views Implemented
    Pitch model, line/keypoint detector, calibrator, any inspection UI Nothing

    Two conventions to fix up front (both currently unspecified):

    1. Image coordinates of H. Detections are normalised top-left xywh and PitchProjector applies H straight to normalised anchors. So we define H as normalised image coords → pitch metres (origin centre spot, +x along the long axis, per projection.md §2). Internally the calibrator works in pixels and converts with H_norm = H_px · diag(W, H_img, 1).
    2. Pitch dimensions per game (game table / match metadata), default 105 × 68. The pitch model is parameterised by them.

    1. Approach¶

    Broadcast main camera = fixed position, pan/tilt/zoom only. That gives a clear progression:

    1. Per-frame homography (8 DOF) from detected pitch features. Enough for ground-plane projection; simplest to get working.
    2. Temporal propagation: calibrate keyframes robustly, carry H between them with frame-to-frame motion (feature tracking on pitch pixels, masking out players), reset on scene cuts (broadcast classifier / shot boundary). Smooth.
    3. Constrained camera model (later): solve the camera position once per game, then per frame only pan/tilt/roll/focal (≤4 DOF). Much more stable on close-ups with few visible lines, and it is what later enables ball height (not just ground shadow).

    Feature detector: pretrained first, own training only if needed¶

    Broadcast pitch calibration is a well-studied task (SoccerNet camera calibration challenge), with public models trained on exactly this kind of footage. Options, to be evaluated in M1:

    Option What it outputs Fit
    Pitch-keypoint pose model (YOLO-pose style, ~30 named pitch keypoints) Keypoints with ids → direct DLT/RANSAC homography Easiest to integrate (ultralytics already a dep); weak when few named keypoints are visible
    Keypoints + line heatmaps (SoccerNet-calibration-style HRNet models, e.g. "No Bells Just Whistles", PnLCalib) Keypoints and line intersections/tangent points → H or full camera Best reported accuracy; heavier, needs GPU for full-clip runs
    Classical, known-size features: white-pixel mask inside pitch → line segments + ellipse fits → identify features (penalty box, goal area, centre circle r=9.15 m, halfway line) by their geometry → solve Named lines/conics → H, and via plane-based calibration (Zhang) focal length + camera pose No training data and fully inspectable; the hard part is identifying which line is which (partial views, symmetric halves, occlusion). Contender for M1 and always used as the refinement step

    The pitch model's known dimensions are what make calibration possible in every option above. The options only differ in how features in the image get matched to their counterparts in that model: hand-written geometric rules or a learned detector.

    Plan: wrap whichever pretrained model wins behind a PitchFeatureDetector interface; add classical line-snapping refinement on top. Licences and weights availability are checked before adopting any of them. Fine-tune on our own frames only if M1 numbers say so (lesson from ball detection: measure before assuming more data helps).

    2. Module layout¶

    src/footy_track/calibration/
  pitch_model.py      # canonical pitch: lines, arcs, named keypoints (metres), param'd by dims
  geometry.py         # DLT/RANSAC homography, px<->norm, reprojection error, warp helpers
  detectors/          # PitchFeatureDetector protocol + pretrained impl(s)
  calibrator.py       # single-frame: features -> H + quality (inliers, reproj err)
  refine.py           # snap model lines to observed white pixels
  temporal.py         # keyframes + frame-to-frame propagation + cut reset + smoothing
  camera.py           # (M4) fixed-position PTZ camera model
  store.py            # write calibration / pitch_keypoint / run rows
scripts/calibrate_clip.py   # CLI: clip -> calibration run in the feature store
labeller/calibration.py + web/calibration.html   # inspection page (§4)

    calibration_quality ∈ [0,1] is derived from inlier count + mean reprojection error so the projector's existing H_quality < 0.3 → NaN gate works unchanged; raw numbers are kept in run diagnostics.

    3. Milestones¶

    # Deliverable Done when
    M0 Pitch model + geometry utils + manual calibration in the inspection page (click ≥4 pitch points → H). Saves clicks as calibration GT. Overlay of reprojected pitch lines sits on the real lines for hand-clicked frames; ~50–100 GT frames across the eval_data/clips
    M1 Single-frame automatic calibrator (pretrained detector + RANSAC + refinement), run on sampled frames Scored against M0 GT: reprojection error (px), % frames calibrated, % within 5 px; ≥2 detector options compared
    M2 Temporal: keyframes + propagation + cut reset + smoothing; calibrate_clip.py writes to the store Whole clips calibrated; jitter metric low; failures flagged rather than silently wrong
    M3 Projection end-to-end: store H → PitchProjector → pitch positions; minimap in the page Players project inside pitch bounds; plausible speeds (< ~10 m/s); formation shapes look right
    M4 Fixed-position camera model; optional fine-tune on own GT Better accuracy on hard frames (close-ups, few lines) vs M2

    Each milestone is its own PR, with tests, against main.

    4. Inspection plan — how you check each step¶

    One page, /calibration in the existing labeller FastAPI app (same hub, same Konva frontend patterns; per the KB, keep overlays as siblings of the Konva stage container). It grows panel by panel with the milestones:

    Panel Shows Catches From
    A. Frame + model overlay Video frame with the canonical pitch lines reprojected through H⁻¹, toggled on/off The main check. Misalignment shows straight away, e.g. a penalty box drawn in the wrong place M0
    B. Feature overlay Detected keypoints/lines with ids, green = RANSAC inlier, red = outlier Detector errors vs fitting errors M1
    C. Bird's-eye warp Frame warped to top-down and alpha-blended over a pitch template Global distortion, wrong-half flips M0
    D. Minimap Top-down pitch with projected players/ball/refs. Hovering a box highlights its dot, and the other way round Projection/anchor bugs, out-of-bounds players M3
    E. Timeline strip Per-frame quality/reproj-error/keyframe/cut markers under the scrubber, with "jump to worst N" Temporal drift, bad stretches, missed cuts M2
    F. Camera-param plots Pan/tilt/focal (or H-derived proxies) over time Jitter and jumps that look fine frame by frame M2/M4
    G. Manual edit Drag points / click correspondences → re-fit, save as GT Produces GT and fixes bad keyframes M0

    Plus a run comparison selector (two calibration run_ids, overlays in different colours) and a non-interactive contact-sheet report (grid of worst/median/best overlay thumbnails + metric table per run) generated by calibrate_clip.py --report, so a batch run can be judged in 30 seconds.

    Checkpoints¶

    • After M0: open a frame, click 4–6 points (corners of the penalty box, centre spot…), confirm panel A lines up across the whole visible pitch and panel C looks like a flat pitch. This validates the pitch model, the coordinate conventions and the maths before any ML. Then label the GT set.
    • After M1: contact sheet of worst-10 frames per detector + metric table vs GT. Decide which detector to adopt and whether fine-tuning is needed.
    • After M2: scrub 2–3 full clips with overlay on; watch timeline strip for red stretches; check params plot is smooth across pans and resets at cuts.
    • After M3: play a clip with the minimap; players should stay in the pitch and move smoothly; sanity metrics (out-of-bounds %, max speed) in the report.
    • After M4: same metrics as M1/M2 re-run; must improve on hard frames without regressing easy ones.

    5. Risks / open questions¶

    • Few visible lines (midfield close-ups): single-frame fails. Mitigated by temporal propagation (M2) and the camera model (M4); until then such frames get NaN + flagged, never a guessed H.
    • Left/right ambiguity: symmetric pitch, so a half-pitch view can map to the wrong end. Use temporal continuity from wider shots, and confirm it in panel C.
    • Player anchor is bottom-centre of the box; occluded feet bias y. Acceptable for v1; panel D will show how bad it is.
    • Compute: laptop has no GPU. HRNet-class detectors on keyframes only are OK on CPU; full-clip runs go to the WSL GPU box.
    • Pretrained weights licensing: confirm before adopting.

    6. Feature store¶

    Full spec: feature_store.md §3.7.

    • Tables. calibration (one row per game, source, run, frame: H as DOUBLE[9], normalised image → pitch m, quality, errors, review_status, origin_*) and pitch_keypoint (one row per correspondence). source ∈ hand_label | claude | classical | model. Runs are run rows with stage=calibration and params_json (model, prompt_version, …).
    • Best calibration. View frame_calibration_best: hand GT (incl. accepted/edited proposals copied into GT) > accepted machine > proposed by highest score; failed/rejected never win; a frame with any not_broadcast row (see below) has no best calibration at all; it reports the winning source/run.
    • Projection. View detections_on_pitch projects every detection in SQL (same anchors and 0.3 quality gate as PitchProjector; NaN when low quality, NULL when uncalibrated).
    • Import. python -m footy_track.feature_store.ingest_calibration --gt-dir <ball_gt_marks> --db <store> [--dry-run] loads calibration_gt/*.json, calibration_proposals/*.json and frame_type/*.json. Re-import replaces; each clip file lands on every game_id alias of that clip that has ball GT, so calibration and ball marks share game_id + frame_index.
    • Inline columns. frame.homography / calibration_quality / calibration_model_version are deprecated and unused.

    7. Pre-labelling with Claude + proposal review¶

    To cut the manual GT effort, footy_track.calibration.prelabel proposes calibrations that a human accepts on a phone (/calibration/review).

    1. Mask + hints (classical, no ML): HSV grass mask -> white-line mask (top-hat, low saturation, blobs removed) -> Hough segments merged into long lines -> numbered candidate points (line/line intersections, line ends, ellipse/line intersections, spots). The mask is good; the candidate points are sparse (iteration 1 measured only 1-3 of 5-6 GT points per frame within reach), so candidates are only optional hints.
    2. Localise (Claude, iteration 2): ClaudeIdentifier gets a stable, cached prefix (system prompt, schema, reference diagram with keypoint ids and straight-line ids) and per frame one image: the frame with a light labelled pixel grid (ticks every 100 px of the sent image). Claude returns points - any clearly visible keypoint from the enum with an approximate x, y (it may cite a hint's candidate_id to take its exact position) - and lines: visible lines by name (e.g. R_PEN_BOX_FRONT, HALFWAY_LINE) with two points on each, plus view info and an unusable flag. MockIdentifier takes the human GT, optionally adds Gaussian noise (sigma in px @1920), drops or mislabels points, and emits noisy line labels: this simulates Claude's imprecise localisation. Prompt is versioned (PROMPT_VERSION, now p2); token usage incl. cache read/write is logged in run params.
    3. Coarse fit: RANSAC DLT over the point labels (a points+lines DLT when fewer than 4 points). No fit -> failed with a reason, never a guessed H.
    4. Line refinement (calibration/refine.py, numpy LM, no scipy): all 8 DOF of H are optimised so that pitch-model lines and arcs, sampled where they project into the image and onto grass, land on the white-line mask. Cost = Cauchy of a distance transform of the mask, coarse-to-fine (40 px truncated+blurred -> 20 -> 8 px sharp). The labels stay in as a weak prior and, because a DLT from a few noisy clustered points can be arbitrarily poor, the refinement is multi-start (the DLT over every 4-subset of the labels plus the all-label fit); the winner is the lowest all-sample DT cost (off-image samples count as a miss, so hiding the model cannot win) plus a small term for label error beyond ~45 px. It is rejected - the coarse H is kept - if the cost does not improve, H is degenerate (singular / horizon across the bottom of the image), too little of the model stays on grass, or the in-view model moved more than 35 % of the image width.
    5. Score = fraction of reprojected model-line samples within a few px of the mask (after refinement) and the final DT residual; both are stored. The proposal keeps pre_refine (coarse H, score, errors) and refine (applied, reason, costs) for the eval. When refinement is applied, correspondences are re-expressed through the refined H (image_label keeps the as-labelled position) so that accept's re-fit of H from the points reproduces it.
    6. Proposals go to <gt dir>/calibration_proposals/<clip>.json (format: see the labeller README §16); accepting writes calibration_gt with an origin. Accepting over a frame that already has GT is a 409; for human GT (no origin) it needs an explicit overwrite=true and the review page asks first. The pipeline skips frames with human GT (or flagged not-broadcast, step 8) by default (--no-skip-gt to include them).
    7. Not a broadcast frame. Sampled frames that are not the main pitch view (replay, close-up, crowd/bench, graphic, goal-line camera) cannot be calibrated; they are marked with one tap (review page "Not broadcast" / key n, editor button) and are distinct from rejected (= the fit is wrong). Claude's view.main_camera_wide == false only shows a badge on the card; nothing is auto-marked. Two records: the proposal's status becomes not_broadcast (prev_status, reviewed_at kept; works for proposed and failed), and a frame-level flag in <gt dir>/frame_type/<canonical clip>.json ({"clip", "frames": {"<idx>": {"type": "not_broadcast", "ts", "run_id"?}}}, atomic write, mode kept) that outlives the proposal. It is a sidecar of its own rather than a section of calibration_gt so that file keeps meaning "frames with a calibration" for every existing reader (pre-label skip, feature-store GT import, GT list) and deleting a GT frame never drops the flag. Marking a frame that has GT (hand or accepted) is a 409 unless overwrite=true, which deletes that GT; accept / GT-save on a flagged frame are 409 until the mark is cleared (DELETE /calibration/api/frame_type/{clip}/{idx} restores the proposals' previous status). Consumers: the pipeline skips flagged frames with --skip-gt; the feature-store import turns the file into calibration rows (review_status=not_broadcast, no H, run frame_type_import) and the views drop such frames (frame_calibration_best none, detections_on_pitch no_calibration); the Ball Check labeller and training export can read calibration.frame_type.not_broadcast_frames. GET /calibration/api/proposals/... also returns NaN stats as null (a failed proposal with a degenerate H used to 500 and could not be shown).
    8. prelabel_calibration eval compares a run with human GT; prelabel_calibration sweep is the noise sweep (success rate at <= 5 / <= 10 px before and after refinement per label-noise sigma): it answers how precise Claude has to be.

    Frames are read by calibration.video.read_frame: OpenCV 5.0 decodes some clips as all-black frames ("Cannot convert interlaced to progressive frames"), so it falls back to the ffmpeg CLI.

    8. Lens distortion (division model)¶

    A homography maps straight pitch lines to straight image lines; broadcast lenses do not. On wide shots the far touchline (long, near the top of the frame) visibly bows, and in the bird's-eye warp that shows as a curved edge and a real line sitting a metre or two off the drawn one (far-field depth is foreshortened: ~1 px of image error at the far touchline is ~0.25 m on the pitch).

    Model. One-parameter division model about the image centre, x_u = c + (x_d - c) / (1 + k1 r^2), r^2 = |((x_d - c) * 2) / (1, aspect)|^2 (r = 1 at the middle of the left/right edge, vertical axis aspect-corrected; code in calibration/geometry.py). H maps the undistorted normalised point to pitch metres, so everything observed in the image (labels, detection anchors, drawn lines) is in distorted coordinates. Measured k1 on this footage is positive (about +0.01 to +0.03): the far touchline sags in the middle, pincushion in this convention, so the model's line bows the same way.

    Storage / back-compat. A record carries distortion: {"model": "division", "k1": .., "centre": [0.5, 0.5], "aspect": 1.7778} next to H. Missing, null or k1 == 0 is exactly the old behaviour (the old cv2.warpPerspective path, byte-identical). calibration rows get distortion_k1 DOUBLE (added by ALTER ... IF NOT EXISTS on existing stores; only a centred lens is accepted by the importer), and frame_calibration_best exposes it.

    Where it is applied. geometry.project_pitch_model/project_polyline_to_image (camera overlay), geometry.warp_to_pitch (per-pixel remap when k1 != 0), reprojection_errors, the labeller /fit, /warp, GT save and proposal accept (points are undistorted before the DLT, the stored H and points reproduce each other), the review/manual pages (they pass distortion through), PitchProjector.project_frame(distortion=...) and the SQL view detections_on_pitch. The SQL direction is image -> pitch, which is closed form (x_u = c + (x - c) / (1 + k1 r^2)), so the view undistorts the anchor itself from distortion_k1 and the stored image_width/height; the difficult inverse (pitch -> image) is only needed for drawing and lives in Python.

    Estimation. refine_homography(..., fit_k1=True) adds k1 as a 9th LM parameter in the two finer stages (the coarse capture stage keeps it fixed), with a quadratic (non-robust) prior pulling it to 0 (K1_PRIOR_PX, scaled by k1_prior) and a clamp at +-0.15. k1=<value> without fit_k1 holds a given value (per clip / zoom level) and the coarse fit then undistorts the labels first. prelabel_calibration run --fit-k1 / --k1 0.012; the default stays off. k1 trades off against H (focal length / tilt) on frames with few lines, so a per-clip value is the safe way to use it.

    9. The far touchline on a high wide camera (Bournemouth)¶

    Failure seen on arsenal_bournemouth_1st_*: the fitted far touchline landed in the stands / on the hoarding (median 30-100 px off the real line at 1568 wide), most visibly at the HALFWAY_TOP junction. Diagnosed from the masks, not the labels (Claude's centre-circle / halfway points were right):

    1. Grass mask leaked. The hue-only test also accepts the dark green-tinted stands and the apron, so "grass" ran up past the hoardings and the line mask filled with hoarding lettering and crowd texture. grass_mask now redoes the mask with a saturation (0.58x) / brightness (0.5x) gate relative to the pitch's own median colour (pitch_colour) when that changes the result; frames it does not change keep the old mask byte-for-byte.
    2. The far touchline was not in the mask at all. From this camera it is 1-3 px, not brighter than the grass (a saturation dip, V ~ grass) so the V top-hat misses it. far_edge_line finds it as a long, thin, pale strip hugging the top edge of the pitch (opening with +-30 deg line kernels so players' legs drop out); it is ORed into lines_mask and also returned as Detection.far_line. It is suppressed if the strip is much brighter than the grass (FAR_MAX_V_RATIO; that is a white board base, which on Arsenal-Man City sits a few metres behind the real white touchline and must not attract the fit) or in the lower 40 % of the frame.
    3. Capture range. With labels only on the centre circle the coarse H puts the far line 70-200 px away, outside the 40 px capture of the DT. refine_homography(far_mask=...) adds a term (wide capture, weight FAR_WEIGHT = 2) pulling whichever model touchline projects highest to the strip, active only when it lands within FAR_MAX_DY_FRAC of the image height of it. fit_and_score passes det.far_line; other callers are unchanged. "On grass" is also tested with a few px margin, because the touchline is the pitch's edge.

    k1 helps further (the circle and the far line cannot both fit a plain homography): --fit-k1 gave +0.05..+0.15 in score on the affected frames, but stays opt-in. Not fixed: frames where Claude gives < 4 usable points, and panned shots where the far line is out of view.

    10. Hard views: Aston Villa and Bournemouth (pinhole camera mode)¶

    What the verdicts looked like. Arsenal-Man City 32/14/15 accepted/rejected/failed, Aston Villa 12/23/4, Bournemouth 0/12/37. Most Villa verdicts and all but a few Bournemouth ones were given on fits made before the lens-k1 and far-touchline changes (rerefined/previous is only set on 5 Villa and 3 Bournemouth records; proposals carry no review timestamp). Findings, from rendering camera view + warp for every rejected frame and decomposing each stored H into a camera (refine.decompose_G: square pixels, centred principal point):

    1. Non-physical homographies. The three Arsenal matches' stored fits put the camera at about (0, -65, 15) m (x along the pitch, y behind the near touchline, z up; Villa accepted median (0, -64, 15), Man City accepted (0, -66, 15)). The Bournemouth rejects have |r1|/|r2| of 1.2 to 5.7 (a real pinhole is 1) and cameras at 7-45 m height. A free 8-DOF H can express such cameras; a centre-circle + halfway-line view (4-5 collinear/near-collinear labels) does not pin it down.
    2. The far-edge strip is the hoarding, not the touchline. On circle-only views the strip term of §9 pulls the model touchline onto the advertising-board base 1-3 m behind the real line; the whole pitch shrinks (Villa seg110 f45: model circle smaller than the visible ring and than Claude's own CC_LEFT/RIGHT labels; removing the term made it match).
    3. Claude's labels on Bournemouth failures are often wrong, not just imprecise (seg030 f154, seg009 f87: points floating on the grass or on the hoarding, 0/9 RANSAC inliers; seg035 f320: the circle's right extreme labelled as a penalty-box point). Not fixable offline; needs a prompt change / relabel (not attempted: <= 10 live calls budget, no evidence for a specific prompt fix).
    4. Villa corner/penalty-box views (seg020, seg140): no visible defect. Overlays sit on the visible lines at full resolution and the rejected frames differ from the accepted f36 by 4-17 px mean, so those verdicts are not explained by fit error that we can see.

    Fix (opt-in --pinhole on run / rerefine). refine_homography(camera=True) replaces the free H by a 7-DOF pinhole camera (log f, rotation, camera centre) with the same cost; starts are the 8-DOF winner and a look-at grid fitted to the labels; CameraPrior can add a per-match camera-position prior (default weight 0: it did not help on the frames tried). It is skipped when the free fit already decomposes to ratio 0.8-1.25. fit_and_score(camera=...) also refits without the far-edge strip and keeps that fit when it lowers the median label error by > 4 px.

    Measured (offline, stored labels, 1 process). 51 frames: see the task report; summary: Bournemouth wide circle frames (f805, f161, f251, f826, f229) go from ratio 1.2-5.7 to exactly 1 with far line on the grass edge and no boards in the warp; Villa rejected frames change by 4-29 px mean; accepted frames change by 2-12 px mean except Man City seg031 f328 (23 px, one regression: the camera fit disagrees with a box line the old fit followed). Not solved: circle-only frames where the model circle is still smaller than the ring (Bournemouth seg015 f586, f251), frames whose far touchline is out of view, and wrong labels (item 3).
